## Working decisions

- **Stack:** use the exact stack requested for this session (pnpm, React/TypeScript/Vite/Tailwind/TanStack Query/React Router, Node 20/TypeScript/Express/Zod, PostgreSQL/Prisma, Vitest, ESLint, Prettier). The spec calls its stack recommendations assumptions and permits alternatives; this prompt fixes the choice.
- **Database hosting:** use the linked Supabase project for hosted PostgreSQL. Keep Prisma as the server-side data layer and sole migration source; the API connects using `DATABASE_URL`, and `DIRECT_URL` is reserved for Prisma schema commands. Docker Compose PostgreSQL remains available for local development. Do not expose Supabase database credentials or service keys to the browser. Supabase Auth is not substituted for the spec-required Express session and role system. **TODO(spec):** set the database password in the ignored `.env` before applying migrations and seeding the hosted project.
- **Scope:** M1–M8 define the delivery breakdown for Phase 1. Offline/sync UI, SMS campaigns, purchasing, loyalty, full reporting, and other Phase 2–4 work remain deferred even where the broader spec describes them.
- **Payment provider:** use a mock provider by default for development and Lipwa when `PAYMENT_PROVIDER=lipwa`. The official Lipwa docs specify a bearer API key, `POST /api/payments`, `GET /api/status?ref=...`, and callback fields including `checkout_id`, `amount`, and `mpesa_code`. They do not document callback signatures or an IP allowlist. Treat the callback as an untrusted notification and verify every result with Lipwa's authenticated status endpoint before changing payment or sale state. **TODO(lipwa):** configure the API key, channel ID, public callback URL, then verify the merchant account and a live minimum-value transaction before production use.
- **Refunds and exchanges:** refund amounts are calculated from the original sale line totals and limited by sold quantities and paid amount. Admin approval chooses whether each item returns to sellable stock or a separate damaged-stock balance. An exchange links the refund to an already-completed replacement sale. **TODO(spec):** confirm return windows and product-type restrictions before enforcing policy rules.
- **Authentication token/session details:** M2 uses opaque server-side sessions with hashed tokens, HttpOnly SameSite cookies, and configured-origin checks. Session duration is 8 hours. **TODO(spec):** confirm whether PIN unlock should use registered device identities once device management is in scope.
- **M2 auth implementation:** use random opaque 256-bit session tokens stored only as SHA-256 hashes in PostgreSQL, delivered in an HttpOnly, SameSite=Strict cookie. Login lockout is 5 failures per normalized identifier/IP in 15 minutes. **TODO(spec):** confirm the desired session duration and whether PIN unlock should use registered device identities once device management is in scope.

## Conflicts and ambiguities found

- **N1 product aspect ratio:** the backlog's N1 asks for 4:3 product artwork, while SPEC §10.1 requires square product imagery. The spec takes precedence; product artwork is square.
- **N1 product title size:** the earlier polish checklist asks for 15 px, outside SPEC §10.1's typography scale. Product titles use the nearest specified size, 16 px.
- **N1 toast placement:** the backlog asks for bottom-center toasts, while SPEC §10.1 places toasts top-right on desktop and at the bottom on mobile. The spec takes precedence; mobile toasts sit above the cart sheet so its actions stay clear.
- **N1 product placeholders:** the backlog asks for type-specific Lucide icons and names; SPEC §10.1 specifies the gold EJ monogram. Placeholders keep the spec's monogram with the type icon and product name so they remain identifiable by type.
- **Glass surfaces:** reserve glass for the login card, modal backdrops (6 px blur), toasts, and at most two small surfaces per screen. Do not use it on scrolling lists, tables, the cart, or product grids.

- The repository has both `/SPEC.md` and `/docs/SPEC.md`; they are byte-identical. This session names `/docs/SPEC.md` as source of truth, so use it and keep the root copy untouched unless asked.
- The source spec's recommended stack is explicitly an assumption and includes alternatives (Fastify, Drizzle, Jest, etc.); the session prompt fixes Express, Prisma, and Vitest. Follow the prompt's exact choices.
- The source spec's Phase 1 is a broad core POS, while this prompt breaks it into M1–M8 and explicitly excludes later-phase features. Where a requested milestone mentions a capability that the source associates with a later phase (for example stock import/counting or a richer admin surface), the requested milestone scope governs this session; do not extend beyond it.
- The source describes optional PDF receipts, but M7 explicitly requires PDF output; include it in M7.
- The source asks for current Lipwa documentation before implementation, while the prompt gives a fallback if it cannot be accessed. No provider field names or authentication mechanism are assumed until documentation is checked.
